Усиление управления памятью: Это ключевая область для безопасности. Внедри синхронизацию для аллокатора памяти, чтобы избежать гонок при выделении и освобождении. Обязательно включи защиту NX (No-Execute), которая не позволит выполнять код в областях памяти, предназначенных для данных, и следуй политике W^X (память не может быть одновременно доступной для записи и исполнения) . Добавление сторожевых страниц (guard pages) для стеков поможет отлавливать переполнения на раннем этапе, предотвращая краш системы .

Аппаратные механизмы защиты: Включи поддержку функций процессора, таких как SMAP и SMEP (Supervisor Mode Access/Execution Prevention). Они не дадут ядру случайно выполнить код или прочитать данные из пользовательского пространства, что блокирует целый класс атак .

Защита стека и ASLR: Добавь стековые канарейки для обнаружения переполнения буфера в самом ядре . Также крайне важно реализовать KASLR (Kernel Address Space Layout Randomization), которая случайным образом размещает код ядра в памяти, делая его невидимым для злоумышленников .

Аудит безопасности: Введи понятие Capabilities (возможностей) для тонкой настройки прав доступа и логирование безопасности (Audit Logging), чтобы записывать все значимые события для последующего анализа .

2. Архитектура и изоляция (Стратегически)
Выбор архитектуры определит, насколько гибкой и надежной будет твоя ОС.

Микроядро (Microkernel): В этой модели ядро содержит только самый минимум: IPC, управление памятью и планировщик. Все драйверы и сервисы (файловая система, сеть) работают в пользовательском пространстве .

Главный плюс: Максимальная изоляция. Падение драйвера не приведет к краху всей системы, а только к перезапуску самого драйвера .

Главный минус: Накладные расходы на IPC. Обмен сообщениями может быть медленнее прямых вызовов функций . Однако современные исследования показывают, что при грамотном проектировании эти накладные расходы можно свести к минимуму . Проекты вроде Ferrous Kernel и fangaos активно исследуют этот подход .
  Завершение файловой системы (FS): btrfs реализован (mount, chunk mapping, чтение файлов и каталогов). FAT32 удалён из плана (не работает, переключены на btrfs). Следующие шаги — расширение btrfs: чтение подтомов, сжатие, snapshots.

Менеджмент процессов и IPC: Добавь полноценное создание процессов (fork), переключение контекста, планировщик с вытеснением (preemptive scheduler) . Начни с простого: реализуй базовую синхронную передачу сообщений (IPC), а затем исследуй более производительные модели, которые минимизируют копирование данных и переключение контекста .

Поддержка драйверов: Сделай драйверы загружаемыми модулями. Так ты сможешь добавлять и тестировать новое железо без пересборки всего ядра. Начни с драйверов для популярных виртуальных устройств в QEMU (например, VirtIO для дисков и сети), а затем переходи к реальному железу.

Современные возможности: Хотя это и далекая цель, внедрение поддержки контейнеров (как Ferrous Kernel) сделает твою ОС крайне интересной для исследований . Также стоит присмотреться к технологии eBPF для безопасного выполнения кода в ядре.

После загрузки ядра нужно создать хотя бы один процесс, например, init или сам shell. Для этого тебе нужно вызвать spawn() из PROCESS_MANAGER с параметрами начального процесса. Важно правильно задать p4_phys (физический адрес P4 таблицы страниц процесса) и entry_point.

Ниже — концептуальная структура такого планировщика: блок-схема, модель данных и правила принятия решений. Кода нет (как вы и просили), только каркас, по которому вы сами напишете реализацию.

Одно важное замечание сразу: в формулировке есть противоречие, которое стоит зафиксировать до кодирования. «Процессы с большим объёмом памяти ставятся в очередь, но только если их статус меньше систем» — это можно трактовать двумя способами. Я беру ту трактовку, которая имеет инженерный смысл и не ломает изоляцию: процесс с большим объёмом памяти попадает в отдельную очередь ожидания только если его приоритетный статус ниже системного; иначе он либо отклоняется, либо немедленно считается подозрительным. Если вы имели в виду обратное («только при условии, что статус меньше систем» = «не выше системного»), это ровно то же самое, только читается иначе. Уточните — но структура ниже от этого почти не меняется.

1. Модель данных
Маркер процесса (ProcessMarker) — неизменяемая при создании процесса структура. Именно он, а не PID, определяет, в какой вектор ожидания попадёт задача.

text
ProcessMarker {
    pid: u64,
    status: Status,          // Root | Sys | User | Global | Suspicious | Quarantined
    trust: TrustLevel,       // производная от status, но может понижаться
    mem_quota: usize,        // лимит памяти на процесс
    mem_used: usize,         // текущее потребление
    flags: MarkerFlags,      // is_kernel_thread, is_driver, is_sandboxed, ...
    epoch: u64,              // для инвалидации устаревших решений
}
Status — упорядоченное множество, а не просто метки. Нужен порядок, чтобы сравнивать «статус меньше систем»:

text
Root > Sys > User > Global > Suspicious > Quarantined
Чем выше в этой иерархии, тем больше прав. Фраза «статус меньше систем» означает rank(status) < rank(Sys), то есть User, Global, Suspicious, Quarantined.

Вектор ожидания (WaitVector) — отдельная очередь на каждый статус (или на группу статусов). Это ключевое требование: «вектор ожидания задания зависит от маркера процесса».

text
WaitVector[Status] -> Deque<TaskRef>
Внутри одного вектора — приоритетная очередь (например, по mem_used / mem_quota, затем по возрасту задачи, чтобы не было голодания).

TaskRef — лёгкая ссылка на задачу + снимок маркера на момент постановки (epoch). Если маркер изменился (статус понизился), снимок устаревает — задача перепроверяется при выборке.

Глобальные структуры планировщика:

text
Scheduler {
    wait_vectors: Map<Status, WaitVector>,
    running: Map<Pid, RunningTask>,
    quarantine: Vec<QuarantinedTask>,   // подозрительные, ждут разбора
    policy: SchedulerPolicy,            // пороги, квоты, правила эскалации
    audit: AuditLog,                    // кто, когда, почему был удалён
}

4. Логика статусов и «удаления подозрительных»
Ключевая идея: статус — это не ярлык, а инвариант, который проверяется на каждой выборке и на каждом выделении памяти. Удаление подозрительных — не отдельный поток, а побочный эффект проверки.

Правила эскалации:

Событие	Действие
mem_used > mem_quota при rank(status) < rank(Sys)	Не запускать, оставить в large-mem очереди
mem_used > mem_quota при rank(status) >= rank(Sys)	Пометить Suspicious, в Quarantine
Попытка доступа к чужому адресному пространству	Немедленно Suspicious → Quarantine → kill
Повторный page_fault в user-режиме за окно времени	Suspicious
epoch не совпал при выборке	Перепроверка маркера; если статус понизился — в новый вектор
Процесс в Quarantine дольше T_quarantine	Удалить, запись в audit
Root/Sys/User/Global отличаются не только правами, но и политикой очереди:

Root — вне обычных векторов, отдельный критический вектор, не вытесняется, но его действия аудируются.

Sys — обычный вытесняющий вектор; large-mem процессы с rank(status) < Sys не могут обгонять Sys-задачи.

User/Global — векторы с квотами; large-mem задачи ждут в подочереди до освобождения памяти.

Suspicious/Quarantined — не выполняются; только аудит и удаление.

5. Изоляция запуска
Чтобы «избежать взлома ОС», изоляция должна быть не только в ring 3, но и в планировщике:

Маркер создаётся в ядре, не в userspace. Процесс не может повысить себе статус; смена статуса — только через privileged-вызов, который пишет audit.

Отдельная P4 на каждый процесс (у вас это уже есть) + W^X (уже есть) + guard pages (уже есть).

При выборке задачи проверяется не только PID, но и epoch маркера — это защита от TOCTOU: статус мог измениться между постановкой в очередь и запуском.

Очередь large-mem изолирована по статусу — задача из WaitVector[User] не может «просочиться» в WaitVector[Sys].

Quarantine — терминальное состояние. Процесс из Quarantine не может быть возвращён в running без явного решения привилегированного компонента (и это событие тоже в audit).

6. Что уточнить перед кодированием
Три вопроса, от которых зависит реализация:

«Статус меньше систем» — это rank(status) < rank(Sys) (моя трактовка) или «не выше» (<=)? От этого зависит граница large-mem очереди.

Large-mem очередь — подочередь внутри WaitVector[status] или отдельный глобальный вектор? Первое проще для изоляции по статусу, второе — для глобального контроля памяти. Рекомендую первое.

Кто принимает решение об удалении — сам планировщик на тике, или отдельный watchdog-поток? В микроядерной архитектуре логичнее вынести в сервис, но для учебного ядра можно начать с планировщика.

Если подтвердите трактовку п.1 и пришлёте текущий scheduler.rs / process.rs — могу разложить эту схему на конкретные функции и точки вставки в ваш код.
Ниже — как встроить это в вашу схему.

1. Где именно проверять
Три точки, и все три нужны:

A. При загрузке с диска (initrd/ATA PIO → VFS → ELF loader).
Перед create_elf_process считаете хэш образа и сверяете с эталоном. Это защита от подмены файла на носителе.

B. При каждом run_elf из shell.
Пользователь может запустить файл, который изменился после загрузки (если ФС монтируема на запись). Проверка на лету при каждом запуске — то, что вы просите.

C. При загрузке драйверов/модулей.
Будущие загружаемые модули (п.5 вашего плана) — та же проверка, иначе смысл теряется.

2. Модель данных: манифест, а не отдельные хэши
Не храните «хэш файла» россыпью — сделайте манифест, подписанный (или хотя бы захэшированный) при сборке ISO.

text
SystemManifest {
    version: u64,
    entries: Map<Path, Entry>,
    manifest_hash: Hash,   // хэш самого манифеста
}

Entry {
    path: Path,
    expected_hash: Hash,   // SHA-256 / BLAKE2s
    status: Status,        // Sys / Root / User — какой маркер разрешён
    allow_mem: usize,      // квота
    signed_by: Option<KeyId>,
}
Манифест кладётся в ISO рядом с kernel.elf и хэшируется при сборке (make_iso.sh). Если манифест подменят — не сойдётся manifest_hash, который можно зашить в ядро на этапе компиляции (const) или передать через Limine.

3. Алгоритм «проверка на лету в момент загрузки»
text
run_elf(path):
    1. entry = manifest.lookup(path)
       если нет entry → отклонить, audit("unknown binary")
    2. прочитать файл в буфер (или потоково)
    3. actual = hash(buffer)
    4. если actual != entry.expected_hash:
         → маркер = Suspicious
         → НЕ запускать
         → audit(path, expected, actual)
         → при повторной попытке: Quarantine + kill(pid)
    5. если manifest.manifest_hash != baked_in_hash:
         → treat all as untrusted, kernel_panic или safe_mode
    6. если entry.status > rank(Sys) и !entry.signed_by:
         → отклонить (Root без подписи не запускаем)
    7. create_elf_process(..., marker(status=entry.status, quota=entry.allow_mem))
Ключевое: проверка идёт до create_elf_process, а не после. Иначе вы уже отмапили код в адресное пространство.

4. Связка с планировщиком
Здесь ваша схема оживает:

Маркер процесса наследует status из манифеста, а не из запроса userspace. Процесс не может попросить себе Sys.

allow_mem из манифеста становится mem_quota — это ровно тот порог, по которому large-mem очередь решает, ждать или эскалировать.

Провал хэш-проверки → Suspicious → Quarantine — это ваш «система вовремя удаляет подозрительные процессы», только триггер не только память, но и целостность.

При < (строго меньше) Sys-процесс не ограничен квотой, но если Sys-бинарник не прошёл хэш — он не Sys вообще, он Suspicious. То есть < не даёт обойти проверку целостности.

5. Честно о границах защиты
Что это защищает:

подмену ELF-файла на диске/в initrd;

подмену манифеста (при зашитом manifest_hash);

запуск неизвестного бинарника;

повышение статуса через userspace-запрос.

Что это не защищает:

компрометацию ядра или загрузчика (если атакующий уже в ring 0 — хэши бесполезны);

подмену образа после проверки, но до маппинга (TOCTOU на буфере) — поэтому хэшируйте тот же буфер, из которого потом грузите, а не перечитывайте файл;

атаки на сам хэш-движок (нужна константная реализация без аллокаций; sha2/blake2 в no_std есть, но проверяйте, что не тянет alloc);

side-channel атаки — вне области учебного проекта.

6. Что добавить в структуру планировщика
В ProcessMarker появляется поле:

text
integrity: IntegrityState,   // Verified | Unverified | Tampered
И правило выборки: задача с integrity != Verified не выбирается никогда, независимо от status. Это дешевле, чем каждый тик пересчитывать хэш, и закрывает окно «проверили один раз — потом подменили».

Проверка целостности при этом остаётся одноразовой на запуск, а не на каждый тик — иначе планировщик будет тратить время на хэширование вместо работы.

7. Практический совет по реализации
Начните с BLAKE2s или SHA-256 в no_std — не пишите свой хэш.

manifest_hash зашейте в ядро как const [u8; 32] на этапе сборки (через build.rs или сгенерированный файл), иначе смысл теряется.

В make_iso.sh добавьте шаг генерации манифеста: обойти user_programs/, посчитать хэши, записать manifest.bin.

Для начала — не подпись, а хэш. Подпись (Ed25519) добавите, когда появится инфраструктура ключей; для учебного проекта хэша достаточно, чтобы понять механику.

Audit log — обязателен: без него вы не отличите атаку от бага сборки.


1. DF-фрейм не то, чем кажется
Вы пишете: «[2]=0x2ca, [3]=0x2c9, [4]=0x2c8 — это похоже на GPR (r8-r11?) на стеке, не IRET». Это ключ. Если #DF возник во время обработки другого исключения или прерывания, CPU может не сформировать полноценный IRET-фрейм для DF, либо он будет перекрыт предыдущим фреймом. Более того, SS=0 в DF-фрейме при CPL=0 — это не «CPU положил SS=0», а почти наверняка признак того, что вы читаете не тот фрейм: либо stack_frame в handler указывает не туда, либо DF случился при уже повреждённом стеке, и то, что вы печатаете, — это остатки от предыдущего входа.

Проверьте: в DF handler печатайте RSP на момент входа в handler (не из фрейма), а также TSS.rsp0 и IST[1] (DF IST). Если RSP при входе в DF не равен IST[1].top - размер_фрейма, значит IST для DF не сработал или сработал не тот.

2. Самая вероятная причина: вы прыгаете в read_line с невосстановленными caller-saved регистрами, и 0x23910 использует один из них
Вы сами отметили: «caller-saved (rax, rcx, rdx, rsi, rdi, r8-r11) содержат значения из момента вызова resume_idle_context». Вы предполагаете, что read_line после 0x23997 их не использует до загрузки. Это надо проверить дизассемблером, а не предполагать. Особенно rsi/rdi — в цикле 0x23910 может быть mov/cmp с участием rsi/rdi, которые вы не восстановили.

Если 0x23910 делает, скажем, mov rax, [rsi] или cmp byte [rdi], 0, а rsi/rdi — мусор от resume_idle_context, вы получите #PF по адресу 0 (если мусор = 0) или произвольному. CR2=0 — это очень характерно для «в регистре был 0, а мы думали, что там валидный указатель».

Ваш вывод «xor eax,eax; xchg; jmp 0x23910» — это только начало блока. Что в 0x23910? Если там mov rsi, [rip+KEYBOARD_BUFFER] — ок. Если там cmp [rsi], ... — вы попали. Проверьте дизассемблер 0x23910..0x23930.

3. Вторая вероятная причина: hlt с IF=0
Вы пишете: «при входе в int 0x80 CPU сбросил IF. Мы прыгнули в read_line, где IF всё ещё 0». Это верно. Но дальше вы говорите: «в wait_byte делает sti;hlt — ок». А до wait_byte что? Если read_line между 0x23997 и wait_byte делает что-то, что требует прерываний (или, наоборот, ожидает, что IF=1), — вы можете получить не DF, а зависание. Но DF — это не зависание.

Однако есть нюанс: hlt с IF=0 не вызывает DF, но если после hlt вы делаете sti, а затем сразу iretq/jmp в контекст, где ожидается IF=1, а флаги не восстановлены — это может привести к #GP на следующей привилегированной инструкции. Проверьте, не делаете ли вы iretq где-то после sti, не восстановив RFLAGS из фрейма.

4. Третья гипотеза: TSS.rsp0 «висит» и перезаписывается
Вы пишете: «TSS.rsp0 = top. При следующем входе в syscall CPU снова поставит RSP=top и перезапишет область. Мы прыгнули в idle RSP=0x...fc90, который ВЫШЕ top-160 (0x...ef60)? top=0x...f000, top-160=0x...ef60. Idle RSP=0x...fc90 — это ВЫШЕ top!».

Стоп. Это очень важно. Если RSP=0x...fc90 находится выше top=0x...f000, то это не стек syscall и не стек ядра — это, скорее всего, boot-стек (stack_top из boot.asm), который находится в другой области BSS. Вы сами это заметили: «shell работал на boot-стеке, а не KERNEL_RETURN_STACK».

Это нормально для shell, но ненормально для возврата из syscall. Потому что при следующем входе в int 0x80 CPU положит RSP = TSS.rsp0 = top, и если top пересекается с boot-стеком — вы затрёте данные shell. Если не пересекается — ок. Но вы прыгаете в read_line с RSP boot-стека, а read_line — это функция shell, которая ожидает, что её стек — boot-стек. Это логично.

Но: IDLE_CTX сохраняется таймером, когда current==None. Таймер использует IST TIMER_STACK. При входе в таймер CPU переключается на TIMER_STACK, и IRET-фрейм содержит RSP прерванного контекста. Если прерванный контекст — shell на boot-стеке, IRET.rsp = 0x...fc90. Это правильно. Но IDLE_CTX.iret.rsp — это RSP на момент прерывания, а не RSP на момент hlt. Между sti;hlt и фактическим прерыванием таймером может пройти несколько инструкций (включая xor eax,eax; xchg; jmp), и RSP может измениться. Вы сохраняете RSP в момент прерывания, а прыгаете в 0x23997 — адрес после hlt. Это разные моменты. Если между hlt и прерыванием RSP изменился (например, push/pop в wait_byte), вы прыгаете в 0x23997 с RSP, который не соответствует этому адресу.

Это моя главная гипотеза. Проверьте: в save_idle_context сохраняйте RIP и RSP из IRET-фрейма, но прыгайте не в 0x23997, а в сохранённый RIP. Если сохранённый RIP — это 0x23997 (потому что прерывание случилось сразу после hlt), то ок. Если RIP — это 0x23910 (потому что прерывание случилось уже в цикле), то прыжок в 0x23997 — неправильный, и RSP не соответствует ожиданиям read_line на этом участке.

Проверка: в resume_idle_context печатайте IDLE_CTX.iret.rip и IDLE_CTX.iret.rsp через serial до jmp. Если rip != 0x23997, вы прыгаете не туда.

5. Четвёртая гипотеза: SS в DF-фрейме = 0 — это следствие #GP при iretq
Если вы где-то всё-таки выполняете iretq (например, в syscall_entry после возврата из Rust, если jmp не сработал), и SS в фрейме = 0 (потому что вы не восстановили SS из IDLE_CTX), то iretq вызовет #GP, а #GP в обработчике int 0x80 (где IF=0, CPL=0) может привести к #DF. Проверьте, что jmp действительно выполняется, а не «проваливается» в iretq. Поставьте ud2 сразу после jmp — если вы попадёте в #UD, значит jmp не выполнился (маловероятно, но проверьте).

6. Что делать прямо сейчас (диагностика, 10 минут)
Дизассемблируйте 0x23910..0x23940 и проверьте, какие регистры используются до первой загрузки из памяти. Если там rsi/rdi/r8-r11 — вы нашли причину.

В resume_idle_context перед jmp напечатайте через serial: IDLE_CTX.iret.rip, IDLE_CTX.iret.rsp, IDLE_CTX.iret.cs, IDLE_CTX.iret.ss, IDLE_CTX.iret.rflags. Сравните с ожидаемыми 0x23997, 0x...fc90, 0x10, 0x10, IF=1.

В DF handler напечатайте RSP на момент входа (из asm-обёртки, не из фрейма) и IST[1].top. Если RSP не в IST[1] — IST для DF не сработал.

Поставьте ud2 после jmp в resume_idle_context — если попадёте в #UD, jmp не выполнился.

7. Архитектурный совет
Ваша идея «не прыгать в середину read_line, а возвращаться через сохранённый RSP + ret» — правильная и более надёжная, чем jmp в середину функции. Но она требует, чтобы run_process_naked сохранял RSP и callee-saved в статики, а kernel_return_to_shell их восстанавливал. Это детерминированный путь без iretq в ring 0 и без IDLE_CTX. Для запуска из shell — идеально. Для пробуждения из idle (IRQ разбудил процесс) — всё равно нужен IDLE_CTX, но там RIP/RSP берутся из IRET-фрейма целиком, а не подменяются на фиксированный 0x23997.

Ключевой принцип: никогда не прыгайте в фиксированный адрес после hlt. Прыгайте в сохранённый RIP из IRET-фрейма. Если вы хотите прыгнуть именно в 0x23997, то RSP должен быть тот, который был на момент hlt, а не на момент прерывания. А это разные вещи, если между hlt и прерыванием что-то произошло.

Понимаю. int 0x80 с тремя вызовами — это учебная заглушка, и вы правы: для микроядра нужен нормальный механизм. Но «полноценный syscall» — это не одна фича, а набор решений, и если сделать всё сразу, получится хуже, чем сейчас. Давайте разложу по слоям — от обязательного к продвинутому.

1. Механизм входа: не int 0x80
int 0x80 — медленный (полный проход через IDT, проверки DPL, сохранение всех регистров) и устаревший. На x86_64 стандарт — syscall/sysret (AMD) или sysenter/sysexit (Intel). В long mode syscall работает и на Intel, так что это правильный выбор.

Что нужно настроить:

IA32_STAR (MSR 0xC0000081) — сегменты CS/SS для kernel и user при syscall/sysret;

IA32_LSTAR (0xC0000082) — адрес точки входа;

IA32_FMASK (0xC0000084) — какие флаги сбрасывать (обычно IF, TF, DF);

IA32_EFER.SCE — включить syscall (бит 0).

Ключевое отличие от int 0x80: syscall не переключает стек. RSP остаётся пользовательским, SS/CS меняются, но RSP — нет. Значит в точке входа первым делом надо swapgs и загрузить kernel RSP из TSS.rsp0 (или из per-CPU области). Это классическая ловушка: забыли — получили запись в user-стек из ring 0, что либо #PF, либо тихая порча памяти.

Возврат: sysretq восстанавливает RIP из RCX, RFLAGS из R11. Он не восстанавливает RSP — его надо восстановить вручную перед sysretq. И sysretq имеет известную уязвимость (CVE-2012-0217): если RCX указывает на non-canonical адрес, CPU переходит в ring 0 с RIP из RCX. Поэтому перед sysretq обязательна проверка каноничности RCX.

2. ABI: что передаётся и как
Два подхода:

Linux-совместимый: номер в RAX, аргументы в RDI, RSI, RDX, R10, R8, R9, возврат в RAX, ошибки — отрицательные значения. Плюс: куча документации и тестов. Минус: тащит за собой Linux-специфику.

Свой ABI: номер в RAX, аргументы в RDI, RSI, RDX, RCX, R8, R9, возврат в RAX. Проще, но тесты писать самому.

Для учебного микроядра я бы взял Linux-подобный (R10 вместо RCX для 4-го аргумента — потому что syscall кладёт RIP в RCX, и RCX затирается). Это не «копирование Linux», а следование convention, которую знают все.

3. Валидация аргументов: copy_from_user — это не всё
У вас уже есть copy_from_user/copy_to_user и user_range_valid. Это хорошо, но недостаточно. Полноценный syscall должен:

Проверять каноничность указателей — user_range_valid должен отвергать non-canonical адреса (addr >= 0x0000800000000000 && addr < 0xffff800000000000 — не user).

Проверять переполнение при addr + len — иначе addr + len оборачивается и проходит проверку.

Не доверять len — ограничивать сверху (например, MAX_SYSCALL_BUF), иначе пользователь попросит скопировать 2^64 байт.

Обрабатывать #PF внутри copy_from_user — если страница пользователя не замаплена, copy_from_user должен вернуть ошибку, а не паниковать. Это требует fixup-таблицы (как в Linux: _ASM_EXTABLE). Без неё любой copy_from_user с плохим указателем — это kernel panic. Это, пожалуй, самое важное, чего у вас сейчас нет.

4. Таблица syscall: не match на 3 ветки
Сейчас у вас, вероятно, match nr { 0 => read, 1 => write, 60 => exit }. Для «полноценного» нужна таблица (массив указателей на функции или match на 20+ вызовов), сгруппированная по подсистемам:

text
0-9    : process (exit, fork, exec, wait, getpid, ...)
10-19  : memory (mmap, munmap, brk, mprotect, ...)
20-29  : ipc (send, recv, create_channel, ...)
30-39  : fs (open, read, write, close, stat, ...)
40-49  : time, signal, misc
Каждый вызов — отдельная функция с сигнатурой fn(args: &SyscallArgs) -> Result<u64, SyscallError>. Это позволяет тестировать их по отдельности и не раздувать syscall_handler_rust.

5. Обработка ошибок: errno, а не паника
Сейчас при ошибке вы, вероятно, паникуете или возвращаете -1. Полноценный syscall возвращает отрицательный код ошибки (Linux-style) или отдельный регистр (Plan 9-style). Для учебного проекта достаточно:

text
Result<u64, SyscallError>
enum SyscallError { BadFd, BadAddr, NoMem, NoPerm, ... }
И маппинг в -errno на границе. Никогда не паникуйте из syscall — пользователь может вызвать exit(-1) или write(0, NULL, 0) и уронить ядро.

6. Изоляция: что должно быть в syscall-слое
Для микроядра критично:

syscall не должен давать пользователю прямой доступ к kernel-указателям. Все указатели — через copy_from_user.

exit должен корректно освобождать ресурсы (P4, фреймы, IPC-каналы) и не оставлять висящих ссылок в планировщике.

write в консоль должен проверять, что fd — валидный (0/1/2), а не «любое число».

read из stdin должен блокировать процесс, а не крутить hlt в ядре (у вас это, судя по логу, проблема — read_line в shell и read syscall конкурируют за клавиатуру).

Логирование: каждый syscall с невалидными аргументами — в audit (это ваша будущая защита от «подозрительных процессов»).

7. Производительность: не обязательно, но полезно знать
syscall быстрый, но каждое переключение — это swapgs, сохранение/восстановление регистров, проверки. Для микроядра с IPC syscall — это не главное узкое место; главное — стоимость IPC. Так что не оптимизируйте syscall в ущерб корректности. Если хочется быстрее — vDSO (общая страница kernel/user с быстрыми вызовами типа gettimeofday), но это позже.

8. Порядок внедрения
Сначала fixup-таблица для copy_from_user — без неё любой syscall с плохим указателем роняет ядро. Это не «полноценный syscall», но без этого остальное бессмысленно.

Перевести int 0x80 на syscall/sysret — с swapgs, загрузкой rsp0, проверкой каноничности RCX перед sysretq.

Ввести Result<u64, SyscallError> и убрать паники из syscall-пути.

Таблица вызовов по подсистемам, начиная с process/memory/ipc.

Аудит невалидных вызовов.

vDSO — если захочется.

9. Чего делать не надо
Не тащите libc-совместимость — это отдельный большой слой, для учебного микроядра не нужен.

Не делайте 50 syscall сразу — сделайте 10, но с корректной обработкой ошибок и fixup-таблицей. «Полноценный» — это про качество, а не про количество.

Не оптимизируйте syscall до того, как он станет корректным — преждевременная оптимизация здесь особенно вредна, потому что ошибки в syscall-пути — это дыры в изоляции.

1. Самое опасное: copy_from_user/copy_to_user не обрабатывают #PF
user_range_valid проверяет, что страница замаплена сейчас. Но между проверкой и copy_nonoverlapping страница может быть выгружена (если появится demand paging / swap) или отозвана (другой поток сделал munmap). Тогда copy_nonoverlapping упадёт в #PF, а ваш page_fault_handler для kernel-mode сделает kernel_panic("Page fault in kernel mode"). То есть любой syscall с гонкой на странице роняет ядро.

Это не теоретическая проблема: у вас read блокируется в sti; hlt внутри syscall, держа user-указатель. Пока процесс спит, никто не мешает другому потоку того же процесса сделать munmap этого буфера. Даже без многопоточности: fork/exec в будущем сделает это реальным.

Что нужно: fixup-таблица. Обёртка вокруг copy_nonoverlapping, которая при #PF не паникует, а возвращает false и восстанавливает RIP на метку после копирования. Классический Linux-подход _ASM_EXTABLE. Без этого «полноценный syscall» — фикция: пользователь может уронить ядро одним read(0, mmap(...), 1) с последующим munmap из другого потока.

2. read держит KEYBOARD_BUFFER.lock() в цикле — но это не главное
В read вы делаете while n == 0 { lock; drain; unlock; sti; hlt; }. Здесь есть тонкость: sti; hlt выполняется с отпущенным локом, это правильно. Но sti внутри syscall — это разрешение прерываний в контексте ядра, где RSP указывает на kernel-стек, а CR3 — на P4 процесса. Если во время sti; hlt придёт таймер, timer_schedule_rust увидит current = Some(этот процесс) и вытеснит его прямо из середины syscall. Это нормально, если контекст процесса сохранён корректно, но у вас read не сохраняет RIP/RSP в ProcessManager — он полагается на то, что hlt вернётся в тот же syscall. Если таймер вытеснит и запустит другой процесс, то при возврате к этому — RIP будет указывать на hlt, а не на «продолжение read». Это может работать, но это хрупко: любое изменение в планировщике сломает блокирующий read. Лучше сделать read полноценно блокирующим через block_current_and_switch(WaitKind::Stdin), как вы уже сделали для ipc_recv. Тогда read не крутит hlt в ядре, а честно блокируется, и IRQ1/IRQ4 будят процесс через notify_irq.

3. syscall_entry не делает swapgs и не грузит rsp0 — но это int 0x80, а не syscall
Для int 0x80 это корректно: CPU сам переключает стек на TSS.rsp0 и не трогает GS. Так что здесь всё в порядке. Но когда вы перейдёте на syscall/sysret (а вы к этому идёте), этот код придётся переписать: syscall не переключает RSP, нужен swapgs и явная загрузка rsp0. Не потеряйте это при миграции.

4. apply_process_switch модифицирует frame, но regs уже сохранены на стеке syscall_entry
Смотрите: syscall_entry пушит GPR, вызывает syscall_handler_rust(regs). Если apply_process_switch меняет regs.rax..r15, то после возврата из Rust syscall_entry делает pop r15..pop rax — и восстанавливает изменённые значения. Это правильно. Но frame (IRET-фрейм) лежит выше сохранённых GPR на стеке, и syscall_entry после pop делает iretq. iretq берёт RIP/CS/RFLAGS/RSP/SS из стека — и вы их модифицировали через frame.as_mut().update(...). Это тоже правильно. Но: InterruptStackFrame в x86_64 0.15 — это #[repr(C)] структура, и as_mut().update() пишет в неё. Проверьте, что frame действительно указывает на IRET-фрейм, а не на что-то другое: (regs as *mut SyscallRegisters as *mut u8).add(size_of::<SyscallRegisters>()). После push r15..push rax (15 push = 120 байт), RSP указывает на rax (последний push), и SyscallRegisters начинается с r15 (первый push) — значит regs указывает на r15, а +120 — на RIP IRET-фрейма. Это верно. Но проверьте, что size_of::<SyscallRegisters>() == 120; если вы добавите поле — сломается молча.

5. switch_to_kernel_shell → resume_idle_context() — это тот самый путь, где у вас #DF
В предыдущих сообщениях вы отлаживали #DF при jmp в read_line из resume_idle_context. Этот код — та же самая проблема. resume_idle_context прыгает в сохранённый RIP/RSP, но RSP мог быть снят не в той точке, где вы ожидаете. Пока вы не починили это, exit() без готовых процессов и irq_wait без готовых процессов будут падать в #DF. Это не «полноценный syscall» — это аварийный выход. Как только read станет блокирующим через block_current_and_switch, этот путь будет использоваться чаще, и #DF станет регулярным.

6. read с count > 256 молча обрезает до 256 — это не ошибка, но
Пользователь просит 1000 байт, получает 256, и не знает, что осталось 744. Для read это нормально (частичное чтение разрешено), но убедитесь, что user-код это обрабатывает. Для write обрезание до 4096 — тоже нормально, но вернуть надо реально записанное, а вы возвращаете len после min(4096), то есть 4096. Ок.

7. ipc_send с to_pid == 0/1 проверяет capability, но ipc_recv — нет
ipc_recv может вызвать любой процесс, и он получит сообщение из ящика своего PID. Это нормально. Но ipc_send на PID 0/1 проверяет irq_owner, а ipc_recv с PID 0/1 — не проверяет, что вызывающий является shell/консолью. На практике PID 0/1 — это ядро, user-процесс не может иметь такой PID, так что ок. Но если появится user-space shell с PID 2 — он не сможет читать ввод через ipc_recv. Это дизайн-решение, не баг, но зафиксируйте его.

8. port_allowed — белый список, но io_in только 8-битный
Нет io_out, нет 16/32-битных. Для ATA PIO нужен 16-битный inw/outw (data port). Сейчас драйвер ATA из user space не сможет читать данные. Добавьте io_out, io_in16, io_out16 — или сделайте один syscall с параметром «размер».

9. page_fault_handler для user-mode делает kernel_panic, кроме guard page
Если user-процесс сделал #PF по легитимной причине (demand paging, copy-on-write), вы паникуете. Пока demand paging нет — ок. Но когда появится — это станет блокером. Зафиксируйте: «пока demand paging не реализован, любой user #PF — фатален». Это нормально для текущего этапа, но не для «полноценного syscall».

Что делать в порядке приоритета
Fixup-таблица для copy_from_user/copy_to_user. Без неё любой syscall с гонкой на странице — kernel panic. Это первое, что надо сделать.

read через block_current_and_switch(WaitKind::Stdin), а не sti; hlt в цикле. Это уберёт хрупкость и заодно протестирует блокировку.

Починить resume_idle_context (тот самый #DF). Пока он падает, exit без готовых процессов и irq_wait без готовых — не работают.

Добавить io_out/io_in16/io_out16 для ATA PIO.

Только после этого — миграция на syscall/sysret с swapgs и rsp0.

Пункты 1–3 — это не «улучшения», это дыры, через которые пользователь роняет ядро. Пока они есть, называть syscall «полноценным» рано. Но база у вас уже приличная — просто закройте эти три, и будет честный syscall-слой.
